# Static site + PWA + Android APK: a repeatable setup

A playbook for standing up a static multi-app site on Cloudflare Pages, served
from a subdomain of a domain whose DNS lives somewhere else, optionally with an
installable PWA and a sideloadable Android APK built in CI.

This document is deliberately generic: it describes the shape, not any one
repo. Substitute throughout:

| Placeholder | Example | Meaning |
| --- | --- | --- |
| `<slug>` | `notes` | the app's subpath, `/notes/` |
| `<project>` | `notes-site` | the Cloudflare Pages project name |
| `<subdomain>` | `notes-site-417` | the **assigned** `*.pages.dev` name — see step 4 |
| `<host>` | `apps.example.com` | the hostname the site is served on |
| `<outdir>` | `site` | the build output directory |

Sections 2, 3's APK workflow, and the PWA invariants apply only if the project
ships a bundled app or a native wrapper. A repo of plain static documents skips
them; the hostname, routing, Pages and DNS work in sections 0, 4, 5 and 6 is
the same either way.

Everything below was executed and verified against a real deployment. Where
something failed, it is recorded as a dead end rather than quietly omitted —
the dead ends cost the most time.

---

## 0. Decide the hostname before you build anything

This is the decision that constrains every other one, and it is easy to get
wrong because it sounds like a detail.

**DNS maps hostnames, not paths.** If `example.com` already serves something —
a Squarespace or Wix site, a marketing page — then `example.com/<slug>` cannot
be pointed at Cloudflare by adding a DNS record. No record routes by path. The
path belongs to whoever answers for the hostname.

So pick one:

- **A subdomain you control** — `apps.example.com/<slug>`. One additive CNAME.
  The existing site, and any email on the domain, are untouched. This is the
  right answer almost always.
- **The apex path** — requires moving the whole zone onto Cloudflare, proxying
  the existing site through it, and adding a Worker route to intercept
  `/<slug>*`. If the domain carries email (check `MX` first), a nameserver
  migration puts mail in the blast radius of a change you are making for a side
  project. Weigh that honestly.

Check what you are dealing with before deciding:

```bash
nslookup -type=NS example.com
nslookup -type=MX example.com
curl -sI https://example.com | grep -i server
```

### Pages, not Workers

Cloudflare's dashboard now funnels "import a repository" into **Workers**. For
this use case that is the wrong product, and the reason is the hostname
decision above:

> **A Workers custom domain requires an active Cloudflare zone.** The docs are
> explicit that you cannot attach one to a hostname with an existing CNAME
> record, or to a zone you do not own.

**Pages** will serve a subdomain whose DNS is hosted elsewhere, via a CNAME to
`*.pages.dev`. If the nameservers are staying put, Pages is the only one of the
two that works. That is not a preference; it is a hard constraint.

### Dead ends, recorded

- **GitHub Pages on a private repo.** `POST /repos/:owner/:repo/pages` returns
  `422 Your current plan does not support GitHub Pages for this repository`.
  Pages is a paid feature for private repos. Make the repo public or upgrade —
  no workflow configuration gets around it.
- **A Workers project for a static site.** The build succeeds, then the deploy
  step runs `npx wrangler deploy`, finds no config, and dies with *"application
  detection logic has been run in the root of a workspace"*. Adding a
  `wrangler.jsonc` fixes that error but leaves you on Workers, which cannot take
  the custom domain. Fix the product choice, not the error.

## 1. Repo hygiene

Four files. All four exist because something broke without them.

### `.gitattributes`

```gitattributes
* text=auto eol=lf

*.bat   text eol=crlf
gradlew text eol=lf

*.png  binary
*.jpg  binary
*.ico  binary
*.jar  binary
*.keystore binary
```

A `gradlew` committed with CRLF from a Windows checkout fails on the Linux
runner with `bad interpreter` before Gradle starts. Note `gradlew` has **no
leading path** — a pattern containing a slash is anchored to the
`.gitattributes` location, so `android/gradlew` silently misses
`apps/<slug>/android/gradlew` in a monorepo.

Also set the executable bit, which `chmod` on Windows will not do:

```bash
git update-index --chmod=+x path/to/android/gradlew
```

Verify both landed:

```bash
git show :path/to/android/gradlew | tr -cd '\r' | wc -c
git ls-files -s path/to/android/gradlew
```

The first must print `0`, the second must show mode `100755`.

### `.gitignore`

Everything Capacitor's `cap sync` generates is build output:

```gitignore
node_modules
dist
<outdir>

apps/*/android/app/build
apps/*/android/build
apps/*/android/.gradle
apps/*/android/local.properties

# Generated by `cap sync` — never hand-edit, never commit
apps/*/android/app/src/main/assets/public
apps/*/android/app/src/main/assets/capacitor.config.json
apps/*/android/app/src/main/assets/capacitor.plugins.json
```

### `.nvmrc`

```
22
```

Read by **both** `actions/setup-node` and Cloudflare Pages, so the Node version
is declared once. Check your bundler's floor — Vite 8 requires
`^20.19.0 || >=22.12.0`, and a major-only pin resolves to the latest matching
release, which satisfies it.

### `.editorconfig`

Ordinary, but worth having before more than one person touches the repo.

## 2. Two build targets, and the invariants between them

If the project ships both a hosted PWA and a native wrapper, one source has to
produce two different builds:

| Target | Base | Service worker | Consumed by |
| --- | --- | --- | --- |
| hosted | `/<slug>/` | yes | the website |
| native | `./` | **no** | the APK |

Absolute `/<slug>/` URLs resolve to nothing inside the APK, which serves from
its own root. And a service worker caching assets that already ship inside the
package is only a way to serve a stale build.

### Select the target with a flag, never an env-var prefix

```json
{
  "scripts": {
    "build": "vite build",
    "build:native": "vite build --mode native"
  }
}
```

**Do not write `NATIVE=1 vite build`.** That is POSIX shell syntax. On Windows,
`cmd.exe` reads `NATIVE=1` as a command name and the build dies — while passing
on the Linux runner. A script that is green in CI and broken on the developer's
machine is the worst failure shape there is, because nothing reports it.

A custom `--mode` still produces a production build; only which `.env` files
load changes. Confirm by comparing the emitted bundle hash between the two
targets — if it is identical, it is the same production build.

### The subpath PWA invariants

A service worker can only control URLs at or below its own location. Get these
out of sync and the app installs cleanly, then launches to a blank page — a
failure invisible until someone actually installs it.

1. Hosted manifest `start_url`, `scope` and `id` **all** equal `/<slug>/`.
2. The service worker registers with scope `/<slug>/`.
3. The native build is relative and emits **no** service worker.

Derive them from one constant so they cannot drift:

```js
const BASE = "/<slug>/";
// manifest: start_url: BASE, scope: BASE, id: BASE
// icons:    src: `${BASE}icon-192.png`
// workbox:  navigateFallback: `${BASE}index.html`
```

Assert all three in CI (step 3) rather than trusting review to catch it.

### Dependency traps

- **`typescript` must be a devDependency** if you have a `capacitor.config.ts`.
  `cap sync` cannot read it otherwise and aborts, so the APK job dies at the
  sync step. This went missing in two separate handoffs of this project. If you
  would rather not carry TypeScript, use `capacitor.config.json` instead.
- **`react-dom` belongs in `dependencies`**, not `devDependencies`. It builds
  either way, which is why it goes unnoticed.

## 3. CI

Two workflows. Keep them separate: the cheap one should fail fast without
paying for the Android toolchain.

### `.github/workflows/ci.yml`

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - run: npm ci
      - run: npm run build

      - name: Check the hosted manifest matches its subpath
        run: node scripts/check-hosted.mjs

      - run: npm run sync:android

      - name: Check the native build is relative and has no service worker
        run: node scripts/check-native.mjs

      - uses: actions/upload-artifact@v4
        with:
          name: <project>-dist
          path: <outdir>
          if-no-files-found: error
```

Put the guards in files rather than inline `node -e` strings — nested quoting
inside YAML block scalars is a reliable source of breakage.

`scripts/check-hosted.mjs`:

```js
import { existsSync, readFileSync } from "node:fs";

const BASE = "/<slug>/";
const m = JSON.parse(
  readFileSync("<outdir>/<slug>/manifest.webmanifest", "utf8")
);

const bad = ["start_url", "scope", "id"].filter((k) => m[k] !== BASE);
if (bad.length) {
  console.error(`x expected ${BASE} for: ${bad.join(", ")}`);
  process.exit(1);
}
if (!existsSync("<outdir>/<slug>/sw.js")) {
  console.error("x hosted build lost its service worker");
  process.exit(1);
}
console.log(`ok manifest start_url, scope and id all ${BASE}`);
```

`scripts/check-native.mjs`:

```js
import { existsSync, readFileSync } from "node:fs";

const html = readFileSync("apps/<slug>/dist/index.html", "utf8");

if (html.includes('"/<slug>/')) {
  console.error("x native index.html contains absolute URLs");
  process.exit(1);
}
if (existsSync("apps/<slug>/dist/sw.js")) {
  console.error("x native build emitted a service worker");
  process.exit(1);
}
console.log("ok native build is relative, no service worker");
```

Those two guards are the point of this workflow. They encode the invariants
from step 2, and they cost about a second.

### `.github/workflows/build-apk.yml`

```yaml
name: Build APK

on:
  push:
    branches: [main]
    paths: ["apps/<slug>/**", ".github/workflows/build-apk.yml"]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  apk:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 21

      # The runner ships the Android SDK; this only accepts the licences.
      - uses: android-actions/setup-android@v3

      - name: Cache Gradle
        uses: actions/cache@v4
        with:
          path: |
            ~/.gradle/caches
            ~/.gradle/wrapper
          key: gradle-${{ runner.os }}-${{ hashFiles('apps/<slug>/android/**/*.gradle') }}
          restore-keys: gradle-${{ runner.os }}-

      - run: npm ci

      # Native target: relative paths, no service worker.
      - run: npm run sync:android

      - name: Assemble debug APK
        working-directory: apps/<slug>/android
        run: |
          chmod +x ./gradlew
          ./gradlew assembleDebug --no-daemon --stacktrace

      - name: Name the APK with the commit it came from
        run: |
          mkdir -p out
          cp apps/<slug>/android/app/build/outputs/apk/debug/app-debug.apk \
             "out/<slug>-debug-${GITHUB_SHA::7}.apk"

      - uses: actions/upload-artifact@v4
        with:
          name: <slug>-debug-apk
          path: out/*.apk
          if-no-files-found: error
```

The APK is debug-signed: fine for sideloading, not for the Play Store, which
needs your own keystore.

## 4. Create the Cloudflare Pages project

The dashboard no longer surfaces Pages project creation. The CLI still does.

```bash
npx wrangler login
```

This opens an OAuth consent in your browser. The scope list is broad — it
includes `email_routing:write` and `email_sending:write` — because it is
Wrangler's blanket CLI scope set, not anything this project uses. Revoke later
with `npx wrangler logout`, or from the dashboard's authorized applications.

```bash
npx wrangler pages project create <project> --production-branch main
```

> **Read the output.** If the name is taken, Cloudflare silently assigns a
> suffixed subdomain — asking for `<project>` can produce
> **`<project>-417.pages.dev`**. That assigned value, not the project name, is
> your CNAME target. Assuming otherwise gives you a domain that never validates.

Confirm it rather than trusting memory:

```bash
npx wrangler pages project list
```

### Deploy

```bash
npm run build
npx wrangler pages deploy <outdir> --project-name=<project> --branch=main
```

**Verify on the `*.pages.dev` URL before touching DNS.** This separates build
problems from domain problems, and it takes thirty seconds.

### Routing and headers

Pages reads `_redirects` and `_headers` from the uploaded directory. Generate
them from your app list so there is no routing table maintained by hand:

```
# _redirects
/<slug>            /<slug>/              301
/<slug>/*          /<slug>/index.html    200
```

```
# _headers
/<slug>/sw.js
  Cache-Control: no-cache, no-store, must-revalidate
/<slug>/assets/*
  Cache-Control: public, max-age=31536000, immutable
```

The trailing-slash 301 is the rule that matters: without it, `/<slug>` resolves
relative requests one level too high. The `200` rewrite only earns its keep if
the app has client-side routing.

`sw.js` must never be cached, or clients pin themselves to an old build.

## 5. Custom domain

**Order matters.** Register the domain on the Pages project *first*, then create
the DNS record. The reverse returns `522` until Cloudflare catches up.

### 5a. Register it on the project

Dashboard, the Pages project, Custom domains, add `<host>`. Or by API:

```bash
curl -X POST \
  -H "Authorization: Bearer $CF_TOKEN" \
  -H "Content-Type: application/json" \
  "https://api.cloudflare.com/client/v4/accounts/$CF_ACCOUNT/pages/projects/<project>/domains" \
  -d '{"name":"<host>"}'
```

It will sit at `status: pending`, `validation: pending`.

### 5b. Add the CNAME wherever your DNS actually lives

| Field | Value |
| --- | --- |
| Type | `CNAME` |
| Name / Host | the subdomain label only, e.g. `apps` |
| Data / Target | `<subdomain>.pages.dev` |
| TTL | default is fine |

Most DNS UIs append the domain, so the name field takes `apps`, not
`apps.example.com`. No trailing dot, no `https://`.

**Add only this record.** On a domain carrying email, the `MX` records and the
apex records are load-bearing and must not be touched.

### 5c. Wait for the certificate

DNS resolving is not the same as being live: Cloudflare still has to complete
HTTP validation and issue a certificate. Expect a few minutes, occasionally
~15. Until then HTTPS fails to connect, which is expected, not broken.

```bash
nslookup -type=CNAME <host> 8.8.8.8
curl -s -o /dev/null -w "%{http_code}\n" https://<host>/<slug>/
```

## 6. Verify

Run all of it. Each check here caught something real at some point.

```bash
H=https://<host>

for p in "/" "/<slug>" "/<slug>/" "/<slug>/manifest.webmanifest" "/<slug>/sw.js"; do
  printf "%-34s " "$p"
  curl -s -o /dev/null -w "http=%{http_code} loc=%{redirect_url} ctype=%{content_type}\n" "$H$p"
done

curl -s -o /dev/null -w "ssl_verify=%{ssl_verify_result} (0=ok)\n" "$H/<slug>/"

curl -sI "$H/<slug>/sw.js" | grep -i cache-control
```

Expected: `/` returns 200, `/<slug>` returns 301 to `/<slug>/`, `/<slug>/`
returns 200, the manifest is served as `application/manifest+json`, `sw.js`
carries `no-store`, and hashed assets carry `immutable`.

Then in a browser, on the real hostname:

```js
const regs = await navigator.serviceWorker.getRegistrations();
const m = await fetch("/<slug>/manifest.webmanifest").then((r) => r.json());
({
  swScopes: regs.map((r) => r.scope),
  triad: { start: m.start_url, scope: m.scope, id: m.id },
});
```

`swScopes` must be `["https://<host>/<slug>/"]` and all three `triad` values
must be `/<slug>/`. **Service worker scope and the manifest triad must agree** —
that agreement is what makes the installed app open to the app instead of a
blank screen.

Finally, confirm you broke nothing on a shared domain:

```bash
curl -sI https://example.com | grep -i server
nslookup -type=MX example.com 8.8.8.8
nslookup -type=NS example.com 8.8.8.8
```

The existing site should still answer, and MX and NS should be exactly what
they were before you started.

## 7. Optional: deploy from CI

Direct upload from a workflow, once you want pushes to publish.

```yaml
name: Deploy to Cloudflare Pages

on:
  workflow_dispatch:
  # push:
  #   branches: [main]

permissions:
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Fail early if the secrets are missing
        env:
          TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          ACCOUNT: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
        run: |
          if [ -z "$TOKEN" ] || [ -z "$ACCOUNT" ]; then
            echo "::error::Add CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID first."
            exit 1
          fi

      - run: npm ci
      - run: npm run build

      - uses: cloudflare/wrangler-action@v3
        with:
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
          command: pages deploy <outdir> --project-name=<project> --branch=main
```

Secrets:

- `CLOUDFLARE_API_TOKEN` — My Profile, API Tokens, Create Token, "Edit
  Cloudflare Workers" template, or a custom token with Account, Cloudflare
  Pages, Edit.
- `CLOUDFLARE_ACCOUNT_ID` — Account Home sidebar, or `npx wrangler whoami`.

Keep it on `workflow_dispatch` until it is green once, then enable the push
trigger. Deploying by hand is a perfectly good end state; this is convenience,
not a requirement.
